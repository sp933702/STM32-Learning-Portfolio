為什麼不能只送 0x9F？
因為 SPI Slave 不會自己產生 Clock。
你現在 STM32 是：
Master
W25Q64 是：
Slave
只有 STM32 可以產生：
SCLK
假設你只做：
送 0x9F
會發生：
CS = LOW
MOSI:
1 0 0 1 1 1 1 1
└──── 0x9F ─────┘
SCLK:
8 clocks
W25Q64 經過這 8 個 Clock 才完整知道：
「喔，Master 要執行 Read JEDEC ID。」
可是問題來了：
W25Q64 接下來準備回：
EF 40 17
但是 STM32已經停止產生 Clock。
結果：
STM32：我送完 0x9F 了，停止 SCLK
W25Q64：
好，我準備把 EF 送出去……
W25Q64：
？？ Clock 呢？
沒有 Clock，Slave 就沒有辦法把資料一個 bit 一個 bit shift 出來。
所以 STM32 必須再製造 24 個 Clock
JEDEC ID 有：
EF
40
17
共：
3 bytes × 8
= 24 clocks
因此 STM32還必須繼續進行三個 byte 的 SPI transfer。
但是 SPI 是 Full-Duplex：
要 Receive，就一定同時也正在 Transmit。
所以為了拿回：
EF 40 17
STM32必須在 MOSI 上「隨便送三個 byte」來換取 Clock。
用 Clock 看會更清楚
整個 transaction 是：

              第 1 byte            第 2 byte     第 3 byte     第 4 byte

SCLK       8 clocks              8 clocks       8 clocks      8 clocks
             │                      │              │             │

MOSI        0x9F                   0xFF           0xFF          0xFF
             │                      │              │             │
             ▼                      ▼              ▼             ▼
W25Q64    收到 Command          不在乎          不在乎        不在乎


MISO        無效                   0xEF           0x40          0x17
                                      │              │             │
                                      └──── JEDEC ID ──────────────┘

為什麼 Dummy 是 0xFF？
其實對 0x9F Read JEDEC ID 這個階段而言，後面的 MOSI 資料 Flash 並不拿來當新的 command。
我們只是需要：
產生 SCLK
所以理論概念上 dummy 可以是例如：
0x00U
或：
0xFFU
但 SPI Flash 通訊很常看到：
0xFFU
作為 dummy byte，因此我們目前使用 0xFFU。
真正重要的不是：
「一定必須送 FF 才能讀到資料。」
而是：
Master 必須繼續進行 transfer，才會有 Clock 讓 Slave 把資料送回來。

SPI Receive 本身也需要 Master 提供 Clock。
所以：
要從 Slave 收 3 bytes
→ Master 還是必須做 3 bytes 的 transfer
→ MOSI 同時送 dummy data
→ MISO 同時取得真正資料

目前實際讀到：
Manufacturer ID = 0xEF
Memory Type     = 0x40
Capacity ID     = 0x17
前兩個先當成識別碼；這一步專注在：
capacity_id = 0x17;
0x17 不是直接代表 64
先轉成十進位：
0x17 = 23
JEDEC Flash 的這個容量編碼可以理解成：
容量（Bytes） = 2 ^ capacity_id
因此你的 Flash：
2^23 Bytes
接著換算：
2^23 Bytes
= 8,388,608 Bytes
= 8 MiB
再乘上：
1 Byte = 8 bits
所以：
8 MiB × 8
= 64 Mbit
因此：
Capacity ID = 0x17
        ↓
decimal 23
        ↓
2^23 Bytes
        ↓
8 MiB
        ↓
64 Mbit
        ↓
W25Q64

0x16 → W25Q32
0x17 → W25Q64
0x18 → W25Q128
會發現 capacity code 每增加 1：
2^22 → 2^23 → 2^24
容量就會：

三個 SPI Command 目前看起來被包在同一次 CS = LOW 裡面了。
這對 W25Q64 不行。它會把 CS LOW 之後收到的第一個 Byte 當成 Command，直到 CS 再次 HIGH，這個 instruction 才結束。
正確做法：每個 Command 都要有自己的 CS LOW → HIGH

SPI Flash 跟 RAM 很不一樣。如果直接開始 Page Program，很容易誤以為「想寫什麼就寫什麼」。
W25Q64 最重要的規則：寫入只能把 1 → 0
Page Program 可以把部分 1 改成 0：
原本：1111 1111
寫入：1010 1010
結果：1010 1010
這沒問題。
但是假設現在 Flash 裡已經是：
1010 1010
你想直接改成：
1111 1111
就不行，因為那需要：
0 → 1
而 Page Program 做不到 0 → 1
要把 bit 恢復成 1，必須先做：
Erase
擦除後才重新變成：
1111 1111
所以整個邏輯是：
Erase
→ 把很多 bit 恢復成 1
Program
→ 選擇性把某些 1 寫成 0

W25Q64 的基本儲存階層
1 Byte   = 8 bits
1 Page   = 256 Bytes
1 Sector = 4096 Bytes
         = 16 Pages
Page Program 是一次最多寫：
256 Bytes
但是 Sector Erase 一次會擦掉：
4096 Bytes
「我要改一個 byte，所以只擦一個 byte。」
Flash 通常不是這樣。
你若做 Sector Erase：
Address 0x000000
        ↓

0x000000 ~ 0x000FFF
這 4096 bytes 全部會被擦成 0xFF。
